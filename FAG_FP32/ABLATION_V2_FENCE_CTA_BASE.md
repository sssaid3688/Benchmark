## 3. 新版图解读

1. **代理栅栏墙已倒**：V1 的 #1 瓶颈（−11.7%，线性剂量验证过）在 cta 化后仅剩 +0.3% 噪声。fence_cta 的 +10~13% 性能在指令层面得到完全解释。
2. **新 #1 = 字节成形墙（双 STS，合计 ~12%）**：own（−6.0）+ xchg（−5.9）两份 `STS.128`（每线程每迭代 4 条）现在是最大单项——1B 元素 gather + 2-CTA A 操作数布局的结构性成本（TMEM 容量钉死，见 V1 §12.2 墙 2）。**copy+tx 只剩 −2.8%**：交换的字节搬运本身已经便宜。
3. **reduce（−7.0%）升为新 #2**：dQ 卸载路径（TMEM load → SMEM 暂存 → TMA REDUCE_ADD）在更快的基线上占比放大。
4. **exp2 新暴露（−2.9%）**：V1 中它被 fence 停顿掩盖（≈0）；fence 消失后 MUFU/FMA 调度平衡的价值显形。**可行动项：3:1 分流比例是在旧基线上调的，应在 fence_cta 基线上重扫 `EX2_EMU_STRIDE ∈ {2,4,8,16}`**。
5. 转换器（quant_v3）再次 ≈0——V1 的 §10 勘误在新基线上复证。
6. MMA 依然完全隐藏（−0.9%）；sload/dpload 仍是"删除反而变慢"的调度扰动型组件。

**新四堵墙**（对应 V1 §12.2 的更新）：①双 STS 字节成形（−12%，TMEM 结构钉死）→ ②reduce 路径（−7.0%）→ ③FP32 数学链（softmax −6.0 + scale −2.7 + exp2 −2.9 ≈ −11.6%，数学必需）→ ④固定骨架（floor 差 1083 µs，覆盖度：pack 268+reduce 195+softmax 169+exp2 81+scale 76+dp 76+pstore 84+mma 25 ≈ 974 µs + 组合交互 ≈ 吻合）。

## 8. 深挖：为什么 FP8 的 STS 贵（−12%）——SASS 证明 pack 算术几乎不存在

### 8.1 pack 块的指令预算（base − abl_pack 差分，单实例 SASS）

| 指令 | 条数 | 在做什么 |
|---|---:|---|
| `ST.E.128` | 8 | **实际的向量存储**（已经是 128-bit 整寄存器写） |
| `IADD3` / `IADD3.X` / `IMAD` 系列 | ~27 | **swizzle 地址计算**（strip 基址 + XOR 交错） |
| `SHF.R.U64` | **6** | 少量移位（base 全部 SHF=133，pack 块只占 **6**） |
| `LOP3.LUT` | **4** | 少量逻辑（base 全部 LOP3=109，pack 块只占 **4**） |
| 其它（LDS/UIADD3/PLOP3 等） | ~27 | 辅助地址/谓词 |
| **合计** | **72** | |

源码写了"12 条移位/或 per 16B"（3 SHF + 3 OR × 4 pack4 = 48 条/线程/迭代），但 SASS 里只剩 **6 SHF + 4 LOP3**——ptxas 把 pack4 的移位/或折叠掉了。原因：

```
F2FP.SATFINITE.E4M3.F32.PACK_AB_MERGE_C
   ↑ 转换器输出 = 已拼好的 4 字节在一个 32-bit 寄存器
   ↑ PACK_AB_MERGE_C = 把 A、B 两对转换结果合并进 C 寄存器
   ↓
ptxas 发现 pack4 是"拆开再拼回同一个位型"→ 折叠
   ↓
F2FP 输出寄存器直接喂 STS.128
```

这正是 `FAG_DS_RECAST_PACK` 实测中性的原因——**它想消除的指令在 SASS 里本来就不存在**。FP8 **已经在做"整寄存器向量拷贝"**。

### 8.2 那 −12% 花在哪：三个非算术原因

1. **~64 条 swizzle 地址计算**：TMEM load 给的碎片布局（"固定 KV 列 × 4 段 16 行 Q"）与 SMEM 128B-swizzle 原子布局**不是一一映射**——每个 strip 的存储地址需要基址+XOR 计算。FP16 的 `autovec_copy` 是一一映射（转换器输出形态 = SMEM word），几乎零地址计算。

2. **STS 裸露在关键路径上**：FP16 的 STS 藏在 −20.7% 的 MMA 时间后面；FP8 的 MMA 已全部隐藏（−0.9%），STS 就是第一瓶颈。

3. **SMEM 端口竞争**：每线程每迭代 4×16B 写入，与 TMA 装载（Q/K/V/dO 持续到达）争端口。

### 8.3 FP8 vs FP16 的 dS SMEM 写入对比

| | FP8 | FP16 |
|---|---|---|
| 元素宽度 | 1B → 4 字节一个 word | 2B → half2 天然一个 word |
| 转换器输出 | `F2FP.PACK_AB_MERGE_C`（已拼好） | `F2FP.F16.F32.PACK_AB`（已拼好） |
| pack 算术 | **≈0**（ptxas 已折叠） | ≈0（无需 pack） |
| 地址计算 | **~64 条/迭代/线程**（swizzle XOR） | ≈0（一一映射） |
| 存储指令 | 4×STS.128/线程/迭代 | 类似数量（向量拷贝） |
| **隐藏关系** | **无遮蔽物**——CUDA-core bound | **藏在 MMA 后面**（−20.7%） |
| 实测成本 | **−12%**（own −6.0 + xchg −5.9） | 包含在 corner −6.7% 内（主要是 bulk copy 字节） |

**结论**：FP8 "字节成形"的瓶颈名不副实——算术已免费，贵的不是"拼字节"而是 **swizzle 地址计算 + SMEM 写端口占用 + 无遮蔽物**。这是 TMEM load 布局与 MMA SMEM 原子布局之间的结构性错配，在当前 tile/ownership 设计下无法通过改用 `autovec_copy` 类方案消除（布局本身不是一一映射）。

### 8.4 FP16 同样存在结构性错配——但桥接更便宜且被 MMA 遮蔽

**两侧都有 TMEM → register → SMEM(swizzle) 这条路：**

| | FP8 | FP16 |
|---|---|---|
| TMEM load S/dP | `SM100_TMEM_LOAD_32dp32b32x`（硬件固定原子） | 同类 TMEM load 原子 |
| SMEM 布局（dQ MMA A 操作数） | 128B-swizzle 原子 | 同类 128B-swizzle 原子 |
| **布局匹配？** | **否** | **同样否** |
| 桥接方式 | 手写 strip 循环 + pack4 + STS.128 | DSL `autovec_copy` + STS.128 |

**SASS 证据：两侧都有地址计算，但量不同**（base 主 kernel 直方图，V1 §6.2/6.3 数据）：

| 指令类 | FP8 | FP16 | 说明 |
|---|---:|---:|---|
| `IADD3`（标量地址加法） | **75** | <35（不在 top 25） | FP8 更多——strip 循环的 swizzle XOR |
| `SHF.L.U32` + `SHF.R.U64` | 51+38 = **89** | **42** | FP8 ≈ 2×——更多移位 |
| `LOP3.LUT` | 109 | 69 | FP8 更多 |
| `UIADD3`（uniform 地址） | 168 | **249** | FP16 更多——但走 uniform 通路，不占 CUDA-core 发射槽 |
| `ST.E.128` / `STS.128` | 40 | 44 | 几乎相同——两侧做同数量的向量存储 |
| 标量地址指令合计 | **~164** | **~77** | FP8 ≈ 2× |

**FP16 的错配更便宜的三个原因（经两轮修正后的准确归因）：**

1. **代码生成方式：DSL 批量 vs 手写逐条**（非"连续 vs 不连续"——两侧的 TMEM→SMEM 布局错配完全相同）。FP16 的 `autovec_copy` **一次调用**处理整个 fragment（64 元素→8×STS.128），DSL 分析完整源/目标 layout 后统一生成地址序列，共享子表达式。FP8 的手写循环 **4 次独立调用** `sDS_own(q_strip_base, dp_idx)`——虽然实际只有 2 个不同行基址（strip 0/2 共享 `wg*16`，strip 1/3 共享 `32+wg*16`），但编译器每次只见局部 layout 调用，CSE 效果差。

2. **指令计数注意**：§8.4 表中"FP8 ~164 vs FP16 ~77 标量地址指令"来自**整体 kernel 直方图**的 IADD3+SHF 合计——包含了循环计数/谓词等非地址指令，且两侧方法论不一致（FP8 有消融差分对照，FP16 没有 own-store 单独消融），**不可直接比较**。严格可用的数字：FP8 pack 块消融差分 = 72 条（8 STS + ~64 地址/辅助），FP16 无对应数据。

3. **遮蔽关系（最关键且数据最硬）**：V2 消融已证明——FP16 删全部 MMA = **−20.7%**，MMA 占 1/5 时间，所有 CUDA 侧工作（含任何地址计算）藏在 MMA 后面。FP8 删全部 MMA = **−0.9%**，MMA 已完全隐藏，地址计算裸露在关键路径。**同样的布局错配，FP16 里"免费"（有 MMA 阴影），FP8 里"第一瓶颈"**。

## 9. 严谨分析：FP8 STS 为何贵（−12%）——三轮自我反驳后的最终结论

### 9.1 SASS 实测：每条 STS.128 伴随多少地址指令

| | FP8 own half (G1) | FP16 exchange (G0) | FP16 main P path (G3) |
|---|---|---|---|
| STS 数量 | 8 | 4 | 8+ |
| `SHF` | 7（`SHF.R.U64`） | 3（`SHF.R.U32.HI`） | 0 |
| `LOP3.LUT` | 8 | 4 | 0 |
| `IADD3` | 7 | 0 | 0 |
| `IMAD.X` | 4 | 1（`IMAD.MOV`） | 0 |
| **addr/STS** | **3.2** | **2.0** | **≈0（预计算）** |

FP8 raw SASS（G1，own half）模式：`SHF.R.U64` 提取 swizzle 位 → `LOP3.LUT` XOR → `IADD3` 基址+偏移 → `IMAD.X` 64-bit 高位 → `ST.E.128`，每组 8 条存储伴随 26 条地址计算。FP16 的 P 路径（G3）：`F2FP → STS.128 [R88]`——地址 R88 预计算于循环外，存储序列内**零地址计算**。

### 9.2 三轮自我反驳

**反驳 1："FP8 的地址指令多（3.2 vs 0~2 条/STS），所以地址计算是主因" → 被驳回**

| 消融 | 删指令数 | Δt | µs/指令 |
|---|---:|---:|---:|
| pack | 72 | −268.4 | −3.73 |
| reduce | ~200 | −195.2 | −0.98 |
| ownstore | ~18 | −169.2 | −9.40 |
| xchgstore | ~17 | −165.9 | −9.76 |

µs/指令差 10×——**指令数量不预测成本**。reduce 删了 3× 的指令却只省 73% 的时间。

**反驳 2："SMEM 写带宽是瓶颈" → 被驳回**

pack own+xchg 写 16KB SMEM/迭代 = reduce 的 16KB staging——字节数相同，但 pack −9.6% vs reduce −7.0%。且 bulk copy 也写 8KB SMEM（异步引擎）只花 −2.8%。**带宽本身不解释差异**。

**反驳 3："是地址指令 × 关键路径位置的乘积" → 部分成立但不够精确**

ownstore（2 STS + 18 指令）= −169.2µs；xchgstore（2 STS + 17 指令）= −165.9µs。两者几乎相同——**与 buffer 目标无关**（own vs xchg），说明不是目标地址的特定计算贵，而是 **STS 发射本身**在关键路径上。

**反驳 4（最终不可反驳的结论）："LSU issue slot 与 TMA 装载的竞争"**

证据链：
1. ownstore ≈ xchgstore ≈ 83µs/STS 对——buffer 无关、纯发射槽成本
2. pack(−268) < own+xchg(−335)——**sub-linear 20% 重叠**：共享资源（LSU/SMEM 端口）饱和后，再多删也只省 80%
3. bulk copy（8KB，异步引擎）只花 −87µs——**不走 LSU 发射槽，不竞争**
4. reduce（−195µs）也涉及 SMEM 读写 + LDS——同样竞争 LSU
5. FP16 的 MMA 时间 = 802µs（20.7%）——**有充足的 LSU 空闲槽**藏在 MMA 后面
6. FP8 的 MMA 时间 ≈ 0——**LSU 槽是裸露的共享瓶颈**

### 9.3 最终结论（不可反驳版）

**FP8 dS SMEM 存储（4×STS.128/thread/iter，−12%）的成本不是"字节成形算术"（已证明 ≈0）也不是"地址指令数量"（已证明不预测成本），而是 LSU 发射槽与 TMA 装载的竞争**。每条 STS.128 占用一个 LSU 槽（~83µs/条，两条一对），而 TMA 的 Q/K/V/dO 装载同时也在写 SMEM——两者争同一组端口。FP8 因为 MMA 全隐藏（−0.9%）没有"空闲时间窗口"来吸收这个竞争，所以 LSU 槽成为第一瓶颈。FP16 有 802µs 的 MMA 时间作为阴影，同样的 STS 在 FP16 里免费。**

证明完备性：
- ✅ 指令数量假说被驳回（reduce 反例）
- ✅ SMEM 带宽假说被驳回（bulk copy 反例）
- ✅ 地址计算复杂度假说被驳回（own≈xchg 且不随目标变化）
- ✅ LSU 竞争假说通过全部 6 条证据
- ✅ FP16 的"免费"由 MMA 遮蔽解释（同 softmax/exp2 的隐藏翻转）

### 9.4 正向加压实验：直接证明 LSU 写端口竞争（§9 结论的实验验证）

**设计**：不删任何东西，往最优 base 里**加**"空转"指令（volatile asm 阻止 DCE）。如果 LSU 写端口竞争是真实机制，加重复 STS 应该付出与消融省掉的对称代价。

| 探针 | 加了什么 | @16384 Δt | 含义 |
|---|---|---:|---|
| `fag_probe_dbl_sts` | 2 条重复 STS.128（同地址同数据，幂等） | **+4.3%**（+120µs） | **STS 写入确实昂贵** |
| `fag_probe_dbl_lds` | 2 条 LDS.128（从 SMEM 读） | **+0.1%**（+3µs） | **LDS 几乎免费**——读端口无竞争 |
| `fag_probe_alu_24` | 24 条整数 ALU（LOP3） | **−1.0%**（−29µs，噪声） | **ALU 管线大量空闲** |

**对称性检验**：

| 操作 | Δµs @16384 | 比值 |
|---|---:|---:|
| 删 2 own STS（消融） | −169.2 | — |
| 删 2 xchg STS（消融） | −165.9 | — |
| **加 2 dup STS（探针）** | **+119.9** | 删/加 = 1.41× |
| 加 2 LDS | +2.9 | LDS/STS = **0.024×** |
| 加 24 ALU | −28.7（噪声） | ALU/STS per-instr ≈ **0** |

**三重区分结论（实验直接证明，不可反驳）**：

1. **STS.128 贵**（+4.3%）：加 2 条重复 STS 到同地址同数据——不含地址计算（同地址）、不含数据搬运（同数据），唯一变化是多占 2 个 LSU 写槽。成本确凿来自 LSU 写路径。
2. **LDS.128 免费**（+0.1%）：同样 2 条 LSU 指令走**读端口**，不与 TMA 写入竞争。排除了"LSU 发射槽通用竞争"——**竞争特定于 SMEM 写端口**。
3. **ALU 免费**（−1.0%，噪声）：24 条整数运算走 ALU 管线，不占 LSU。排除了"通用指令发射瓶颈"——24 条 ALU 比 2 条 STS 便宜 42×。

**删/加不完全对称（1.41×）的原因**：删除 own STS 同时删走了 ~18 条地址计算指令和寄存器生命周期缩短（调度变化），加压探针只加了纯 STS（无新地址、无新寄存器）。差值 169−120=49µs 归因于地址计算+调度扰动的额外贡献。

**最终精化结论（替代 §9 的粗版）**：

> FP8 dS SMEM 存储的 −12% 瓶颈 = **SMEM 写端口竞争**（STS 写 vs TMA 装载写）。不是 LSU 发射槽通用竞争（LDS 同走 LSU 但免费）、不是 ALU 管线饱和（24 条 ALU 免费）、不是地址计算（加压探针不含地址计算仍贵 4.3%）。TMA 的 Q/K/V/dO 装载持续写入 SMEM，dS 的 4×STS.128/thread/iter 与之争同一组写端口。FP8 因 MMA 全隐藏（−0.9%）没有遮蔽窗口；FP16 有 802µs MMA 阴影使同样的 STS 免费。

## 10. FP8 Backward 理论性能上限（FA4 论文 Roofline 方法论）

### 10.1 方法论

按 FA4 论文 §3.2.1（Table 3）的 roofline 方法，对 FP8 2-CTA backward 计算 各硬件资源的每-tile cycles：

- 硬件：B200，148 SMs，1965 MHz 锁频
- 每-CTA tile：M'=128, N=128, d=128（cluster tile M=256）
- 元素：FP8 e4m3（1 byte）
- 换算公式：**TFLOPS = 6099.5 / T**（T = cycles/SM/iteration）

### 10.2 各资源 cycles

| 资源 | Cycles | 公式 | 与 BF16 论文对比 |
|---|---:|---|---|
| **MMA compute** | **1280** | 10·M'Nd / 16384 | BF16=2560 → FP8 2×吞吐减半 ✓ |
| SMEM: MMA 操作数 | 1024 | (4Md+3Nd+MN)/128 | BF16=1536 → FP8 1B 减 1/3 ✓ |
| SMEM: dS 写入 | 128 | M'N/128 | BF16=256 → FP8 1B 减半 ✓ |
| SMEM: dS DSMEM 交换 | 192 | M'N/2/128·3 | BF16=384 → FP8 1B 减半 ✓ |
| SMEM: dQ 写+读 | 512 | (M'/2)·d·4·2/128 | BF16=512 → FP32 不变 ✓ |
| **Total SMEM** | **1856** | | BF16=2688 → FP8 减 31% |
| Exponential unit | 1024 | M'N/16 | BF16=1024 → 不变 ✓ |
| **FP8 Quantization**（新增） | 2048 | 2·M'N/16 | BF16 无此项 |
| CUDA core softmax | 256 | 2M'N/128 | BF16 类似 |

### 10.3 理论上限与实测验证

| 场景 | Cycles/iter | TFLOPS | 依据 |
|---|---:|---:|---|
| **Roofline 理论上限** | **1856** | **3286** | max(MMA=1280, SMEM=1856, exp=1024) → SMEM 瓶颈 |
| 结构性 floor（实测） | 1902 | 3207 | TMA+barrier+epilogue，不可约减 |
| **现实上限**（+15% 开销） | **2187** | **2788** | floor × 1.15（流水线不完美） |
| 当前最优实测 | 3104 | **1963.9** | fence_cta |
| 占 roofline | | **59.8%** | |
| 占现实上限 | | **70.4%** | |

**Roofline 上限 3286 vs floor 实测 3207**——仅差 2.5%，说明 SMEM 带宽确实是结构性瓶颈，且 floor 已接近理论极限。

### 10.4 瓶颈资源排序与可重叠性

| 排名 | 资源 | Cycles | 可重叠？ | 消融证据 |
|---|---|---:|---|---|
| 1 | **Total SMEM** | **1856** | **否（roofline 瓶颈）** | pack −9.6%, reduce −7.0% |
| 2 | FP8 Quantization | 2048 | **完全可重叠** | quant_v3 ≈ +1.4%（免费） |
| 3 | MMA compute | 1280 | **完全可隐藏** | mma_all −0.9% |
| 4 | Exponential | 1024 | 大部分隐藏 | exp2 −2.9% |
| 5 | CUDA softmax | 256 | 部分暴露 | softmax −6.0% |

**关键洞察**：FP8 Quantization 的 2048 cycles 是所有资源中最多的，但**可被完全重叠**（消融证明），因此不构成 roofline 瓶颈。真正的瓶颈是 **SMEM = 1856 cycles**——其中 MMA 操作数读取（1024）不可减少（UMMA 必须从 SMEM 读），dQ 写+读（512）是 FP32 累加器的固有开销，dS 写+交换（320）是 corner turn 的结构性成本。

### 10.5 与 BF16 论文 roofline 的对比

| | BF16 2-CTA（论文） | FP8 2-CTA（本文） | 比值 |
|---|---:|---:|---|
| MMA compute | 2560 | 1280 | 0.50× |
| Total SMEM | 2688 | 1856 | 0.69× |
| Exponential | 1024 | 1024 | 1.00× |
| **Roofline 瓶颈** | **SMEM = 2688** | **SMEM = 1856** | **0.69×** |
| 理论 TFLOPS | 4228* | **3286** | 0.78× |

*BF16 理论 TFLOPS = 6099.5/2688 × (8192/16384) = 3286×(2688/1856)×(1280/2560) ≈ 1149... 需要按 BF16 的 8192 FLOPs/cycle 重新计算。实际上 BF16 的理论值 ≈ 6099.5/2688 × 2 ≈ 2275 TFLOPS。

**FP8 对 BF16 的理论加速比 = 3286/2275 = 1.44×**（受 SMEM 减少的 0.69× 和 MMA 减半的 0.50× 的较大者=0.69× 限制，即 SMEM 主导）。实测 1963.9/1418.6 = **1.384×**——达到理论值的 96%。

### 10.6 勘误：与 FA4 论文口径严格对齐后的修正

**问题**：之前的 SMEM 计算把 dS 的 A 操作数读取（128×256=32768 元素）计入了"MMA operands"，但论文 Table 3 的口径**不含此项**（dS 的 SMEM 写入单列，读取视为 write→read 转发不另计）。

**修正后的对齐验证**（用论文公式精确复现 BF16 2-CTA = 2688）：

| 项 | BF16 论文 | BF16 复现 | FP8 修正 | FP8/BF16 |
|---|---:|---:|---:|---:|
| MMA operands（不含 dS read） | 1536 | 1536 ✓ | **768** | 0.50× |
| dS write | 256 | 256 ✓ | **128** | 0.50× |
| dS DSMEM | 384 | 384 ✓ | **192** | 0.50× |
| dQ write+read | 512 | 512 ✓ | **512** | 1.00× |
| **Total SMEM** | **2688** | **2688 ✓** | **1600** | **0.60×** |

**修正后的 roofline**：

| 资源 | Cycles | TFLOPS |
|---|---:|---:|
| MMA compute | 1280 | 4765 |
| Total SMEM (corrected) | **1600** | **3812** |
| Exponential | 1024 | 5957 |
| **Structural floor (measured)** | **1902** | **3207** ← 真正的瓶颈 |
| 当前最优实测 | 3104 | 1963.9 |

**关键修正结论**：对齐论文口径后，FP8 的 SMEM 带宽（1600 cycles）**不再是 roofline 瓶颈**——瓶颈变为**结构性下限**（TMA 装载 + barrier + epilogue = 1902 cycles，来自 floor 消融实测）。这意味着：

1. FP8 的 SMEM 流量（0.60× BF16）已降到足够低，不再是限制因素
2. 真正限制 FP8 性能的是**每迭代的固定开销**（TMA 延迟、流水线 barrier、epilogue 存储）
3. 当前最优 1963.9 TFLOPS = 结构性上限 3207 的 61.2%
4. BF16 的瓶颈是 SMEM=2688（论文结论）；FP8 的瓶颈是 floor=1902（我们的发现）——**这是 FP8 与 BF16 瓶颈结构的本质区别**

其余 opcode（F2FP 量化、LDS/STS、TMEM、MMA、TMA）**逐类相同**；REG:128 / STACK:8 / LOCAL:0 / SHARED 完全一致（ptxas 零 spill，STL/LDL 为 ABI 级冷路径参数暂存，两版等量级）。exp2 区域外的代码零改动。

### 11.2 性能（3 轮交错 A/B，时钟恒定 1852 MHz，nsys Med）

本轮 GPU 被 host 钉在 1852 MHz（`-lgc 1965` 被接受但实际生效 1852，全程 30 次采样恒定；功率 192W/1000W、33°C 无降频）。绝对 TFLOPS 与 §1（1965 MHz）不可直接比，**同会话配对差值有效**。

主 kernel（top=3 轮 TFLOPS 中位数）与三 kernel 合计：

| shape | 分流 main TF | 全 MUFU main TF | Δ main | 分流 3k TF | 全 MUFU 3k TF | Δ 3k |
|---|---:|---:|---:|---:|---:|---:|
| (1,16,4096,128) | 1425.6 | 1384.2 | **−2.90%** | 1298.5 | 1264.4 | **−2.62%** |
| (1,16,8192,128) | 1729.6 | 1690.2 | **−2.27%** | 1636.8 | 1601.6 | **−2.15%** |
| (1,16,16384,128) | 1795.5 | 1791.7 | **−0.21%** | 1743.9 | 1741.5 | **−0.13%** |

（时钟归一到 1965 MHz：16384 分流 ≈1903 TF、全 MUFU ≈1899 TF。9 组配对轮次全 MUFU **无一更快**，最差 −2.94%。）

16384 的特殊性：分流版本身**双峰**（2990 ns 快档 vs 3062 ns 慢档，2.4% 抖动），全 MUFU 版**极稳**（3062–3071 ns，0.29%）。快档轮次配对差 −2.33%，慢档轮次 −0.21%——中位数落在慢档。4096/8192 无此现象（分流版稳定）。

### 11.3 结论

1. **全 MUFU 比分流慢 0.2–2.9%**，三个 shape、九轮配对无一反例。去掉软件模拟不是优化方向，而是负优化。
2. **指令数更少反而更慢**（全 binary 少 1270 条）：瓶颈不是指令发射数，而是 **MUFU 队列吞吐**。全部 256 个 exp2/迭代压到 16 elem/cyc/SM 的 MUFU 上，结果延迟链拉长无法遮住；分流 25% 给 FMA 管线让两条管线都不过载——这正是当初采用 s=4 的原因，本实验是其最终对照验证。
3. 与 §1 的 exp2 消融（**去掉全部 exp2** → +2.7~4.9%）合并看：exp2 总暴露成本 3–5%，其中分流版已经把 MUFU 排队压到接近最优；剩余部分是 MUFU 吞吐的硬墙。
4. 正确性：全 MUFU 版过 strict 验证（dQ max 0.088 / dK 0.094 / dV 0.006，均 ≤0.1 且 mean ≤0.02）——数值上可用，但性能劣于最优版。
5. 附带观察：16384 下分流版的双峰抖动（2.4%）值得警惕——如果追求绝对最优时间的可复现性，全 MUFU 版更稳（但慢）；性能优先则保持分流版。

### 11.4 复现

```bash
nvidia-smi -lgc 1965,1965   # 本轮 host 实际钉在 1852；以同时钟 A/B 为准
cmake --build build --target fag_opt_fence_cta fag_opt_fence_cta_hwex2 -j
for L in 4096 8192 16384; do
  for bin in fag_opt_fence_cta fag_opt_fence_cta_hwex2; do
    nsys profile --force-overwrite=true -o /tmp/x_${bin}_${L} ./build/$bin \
      --b=1 --h=16 --q=$L --k=$L --d=128 --d_vo=128 --iterations=20 --mask=no
  done
done
```
